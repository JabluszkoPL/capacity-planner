Jira Tracking for Planner

A new Tracking tab that links a Jira initiative to a Planner plan, pulls the initiative's epics and time tracking, tells you whether delivery is on track and how much of the plan's buffer has been spent, and lets you lay out the next sprint against today's reality instead of the original dates.

Status: Draft spec, ready to split into agent tasks Date: 2026-09-15 Target repo: this repository (the earlier browser-only Planner is superseded) Jira: Jira Cloud, acme.atlassian.net
How to use this document. Sections 1–9 are the design. Section 10 is a list of self-contained tasks (JT01…JT16); each one can be pasted into an agent together with this file and the repo's CLAUDE.md. Section 11 says which tasks can run in parallel.

1. Summary

Goals

  • Remember a Jira initiative per tracker. Paste an initiative link once; Planner keeps it (synced across devices like everything else).
  • Refresh on demand. One click downloads the initiative's epics, their child issues and their time tracking (original / spent / remaining). "Refresh all" on the list page.
  • Compare against a chosen plan. Pick one Planner project (a plan option) as the baseline. Compare actual progress with the plan without its buffer, and show how much of the buffer is already consumed.
  • Check every few days. Each refresh stores a sample, so the buffer trend is visible over time and you can see when you start eating into it.
  • Plan the next sprint. Tick open Jira issues from the epics, assign people, set estimates and start dates, see computed due dates and a mini timeline, and optionally write Start/Due dates back to Jira.

Non-goals (v1)

  • Two-way sync of scope. Planner's epics/tasks are not created or edited from Jira, and Jira issues are not created from Planner.
  • Task-level matching between plan tasks and Jira issues. Comparison happens at epic level (see §7); tasks finishing in a different order than planned is expected and fine.
  • Assignee write-back, worklog write-back, sprint creation in Jira.
  • Storing Jira credentials in the synced database. They stay on the device.

2. Concepts

TermMeaning
TrackerThe new entity. One Jira initiative + one optional baseline Planner project + the last Jira snapshot + history samples + a sprint draft.
InitiativeThe Jira issue (type Initiative) that groups epics. In many Jira setups, epics hang under it either by parent or by the "Initiative" issue link (initiates / is initiated by); both are supported.
SnapshotWhat one refresh returned: initiative fields, epics, their children, time tracking, statuses. Stored as one JSON payload on the tracker row (like plans.payload): derived data, regenerable.
Baseline planThe Planner project selected on the tracker. Its stored plan is the buffered plan; the spec re-runs the scheduler with buffer: 0 to get the unbuffered plan used for comparison.
BufferTwo views of the same thing. Effort buffer: Σ estimates × project.buffer%. Schedule buffer: working days between the unbuffered plan's finish and the buffered plan's finish. The status panel reports both; "buffer used" is measured in schedule days.
Earned daysPlan days worth of work that Jira says is done, summed over mapped epics: planned days of the epic × the epic's completion ratio.
Earned schedule (ES)The date on the unbuffered plan's cumulative curve at which the plan expected to have earned what has actually been earned today. Today − ES (in working days) is the schedule variance.
Epic mapJira epic key → Planner epic id (or null = "extra scope, not in plan"). Auto-matched by name, editable.
Sprint draftA hand-picked list of open Jira issues with person, estimate, start, and computed due date, scheduled from a chosen sprint start, not from the plan.

3. User flows

Flow 1 — Set up a tracker

  1. Open Tracking in the header. If Jira is not configured yet, a "Connect Jira" panel asks for email + API token (base URL is prefilled from the first link pasted). "Test connection" calls /rest/api/3/myself.
  2. Paste an initiative link (or a bare key such as ACME-12345). Planner parses base URL + key, creates the tracker named after the key, and navigates to it.
  3. Press Refresh. The epics table fills: key, name, status, children count, original / spent / remaining (in days at 8h/day, configurable), start/due if set. Initiative totals sit above it.
  4. Choose a baseline plan from the project dropdown. Epics auto-map by name; fix mismatches in the mapping panel.

Flow 2 — The every-few-days check

  1. Open the tracker (or press Refresh all on the list). Stale snapshots (older than 3 days) show a badge.
  2. Read the status line: Ahead by 2.0 days, On plan, Using buffer: 5.0 of 20 days (25%), or Buffer exhausted, 3.0 days late.
  3. Scan the per-epic table for the epics driving the variance (planned days vs earned days vs Jira remaining).
  4. The history table/sparkline shows the last samples, so the trend (buffer being eaten faster or slower) is visible.

Flow 3 — Plan the next sprint

  1. In the Sprint section set the sprint window (defaults: next Monday, +2 weeks).
  2. Tick open issues from the epics list (grouped by epic, done issues hidden). Each becomes a draft row with: assignee (Planner member), estimate days (prefilled from Jira remaining, else from the mapped plan epic's average task size), start date (defaults to sprint start).
  3. Due date is computed with the scheduler's simulateSpan: weekends and the person's off-days skipped, person speed applied. "Auto-stack per person" chains a person's items back-to-back.
  4. Rows that end after the sprint end are flagged; people whose draft days exceed their sprint capacity are flagged.
  5. The mini Gantt (reusing the existing timeline components) shows the draft; the baseline plan's bars for the same issues' epics are drawn faintly behind for comparison.
  6. Optional: Apply dates to Jira opens a preview (key, summary, old → new Start date / Due date), requires explicit confirmation, and reports per-issue results.

5. Data model

All shapes live in packages/core/src/types.ts, the single contract. New fields follow the repo rule absent field = backward-compatible default.

// packages/core/src/types.ts (additions)

export interface AppState {
  projects: Project[];
  teams: Team[];
  /** Jira trackers. Absent on states saved before tracking existed = []. */
  trackers?: Tracker[];
}

export interface Tracker {
  id: ID;
  name: string;
  /** The link as pasted, kept for display / "open in Jira". */
  initiativeUrl: string;
  /** e.g. "ACME-12345", parsed from the link. */
  initiativeKey: string;
  /** e.g. "https://acme.atlassian.net", parsed from the link. */
  baseUrl: string;
  /** Baseline Planner project to compare against. Absent = none selected. */
  projectId?: ID;
  /** Hours that make one Planner day when converting Jira seconds. Absent = 8. */
  hoursPerDay?: number;
  /** Jira epic key -> Planner epic id, or null = explicitly "not in plan". */
  epicMap?: { [jiraEpicKey: string]: ID | null };
  /** Last refresh. Absent = never refreshed. Derived from Jira; regenerable. */
  snapshot?: JiraSnapshot;
  /** One sample per refresh day (same-day refresh replaces). Oldest first. */
  samples?: TrackerSample[];
  sprintDraft?: SprintDraft;
}

export interface JiraSnapshot {
  fetchedAt: string;           // ISO datetime
  initiative: JiraIssue;
  epics: JiraEpic[];
  /** Custom field ids resolved on this instance, so the UI can label them. */
  fieldIds: { startDate?: string; sprint?: string; storyPoints?: string };
}

export interface JiraIssue {
  key: string;
  summary: string;
  issueType: string;           // "Epic", "Story", "Task", "Bug", "Initiative"…
  status: string;              // display name
  statusCategory: "new" | "indeterminate" | "done";
  assignee?: { accountId: string; displayName: string };
  parentKey?: string;
  originalEstimateSec?: number;
  remainingEstimateSec?: number;
  timeSpentSec?: number;
  startDate?: string;          // ISO date (Jira "Start date" custom field)
  dueDate?: string;            // ISO date
  resolutionDate?: string;     // ISO datetime
  sprint?: string;             // active/last sprint name, if any
  updated: string;             // ISO datetime
}

export interface JiraEpic extends JiraIssue {
  children: JiraIssue[];
  /** Sums over children (seconds). Computed at snapshot time, never trusted from Jira's aggregate fields. */
  totals: { originalSec: number; spentSec: number; remainingSec: number; done: number; all: number };
}

export interface TrackerSample {
  date: string;                // ISO date of the refresh
  plannedDays: number;         // unbuffered plan's cumulative planned days as of `date`
  earnedDays: number;
  varianceDays: number;        // positive = ahead
  bufferUsedDays: number;      // max(0, -varianceDays), capped at bufferDays
  bufferDays: number;          // schedule buffer available (working days)
  jiraSpentDays: number;
  jiraRemainingDays: number;
}

export interface SprintDraft {
  start: string;               // ISO date
  end: string;                 // ISO date, inclusive
  items: SprintDraftItem[];
}

export interface SprintDraftItem {
  issueKey: string;
  memberId?: ID;               // team member or helper; absent = unassigned
  estimateDays: number;
  start: string;               // ISO date, user-set (defaults to sprint start)
  /** Filled after a successful Jira write-back. */
  applied?: { at: string; startDate: string; dueDate: string };
}
Persistence checklist for every new field (from CLAUDE.md): add it to packages/db/src/rows.ts (descriptor + payload projection) or it silently does not persist; add a migration, never edit V1; make canonicalState() treat trackers: [] and absent trackers as equal; extend the conformance suite, not one store's tests.

Not in the model

  • Credentials (email, API token) — device-local only, see §6.2.
  • Plan tasks ↔ Jira issues — no per-task link in v1.

6. Jira access

6.1 Link parsing

parseIssueLink(input, fallbackBaseUrl?) in packages/jira accepts all of these and returns { baseUrl, key } or a typed error:

https://acme.atlassian.net/browse/ACME-12345
https://acme.atlassian.net/browse/ACME-12345?atlOrigin=…
https://acme.atlassian.net/jira/software/c/projects/ACME/issues/ACME-12345
https://acme.atlassian.net/jira/software/c/projects/ACME/boards/551?selectedIssue=ACME-12345
https://acme.atlassian.net/jira/plans/123/scenarios/123/timeline?selectedIssue=ACME-12345
ACME-12345                       (bare key → needs fallbackBaseUrl from settings)

Key regex: /\b([A-Z][A-Z0-9_]+-\d+)\b/ on path first, then on selectedIssue. Base URL = origin. Hosts must end in .atlassian.net unless the settings allow a custom host.

6.2 Credentials

  • Jira Cloud Basic auth: Authorization: Basic base64(email:apiToken). Token from id.atlassian.com → Security → API tokens.
  • Stored by apps/web/src/lib/jiraSettings.ts under localStorage["planner_jira_v1"] as { baseUrl, email, apiToken, hoursPerDay, allowWrites }. Read/write wrapped in try/catch. Never part of AppState, never diffed, never synced, never in the JSON export.
  • The Mac app uses the same renderer storage in v1. Moving the token behind Electron's safeStorage is a listed follow-up (JT16).
  • The Settings panel shows the email and a masked token, has Test connection (GET /rest/api/3/myself), Clear, and the hours-per-day and "allow writing dates to Jira" toggles.

6.3 CORS and the transport seam

Jira Cloud's REST API does not answer browser cross-origin requests, so a plain browser tab cannot call it directly. The web bundle therefore talks to a small JiraTransport interface and the runtime picks an implementation, exactly as apps/web/src/runtime.ts already picks a LocalStore:

  auth: string;                    // "Basic …" — built by the caller, never stored by a transport
  body?: unknown;
}
export interface JiraResponse { status: number; body: unknown; }
export interface JiraTransport {
  readonly canWrite: boolean;
  request(req: JiraRequest): Promise<JiraResponse>;

6.4 Endpoints, JQL and fields

StepCallPurpose
0GET /rest/api/3/myselfTest connection; display name in settings.
1GET /rest/api/3/fieldResolve custom field ids by name: "Start date" (typically customfield_10015), "Sprint" (customfield_10020), "Story Points" (customfield_10037 here). Cached in settings for 24h.
2GET /rest/api/3/issue/{KEY}?fields=…The initiative itself (summary, status, due date, start date).
3POST /rest/api/3/search/jqlEpics of the initiative. Try in order until one returns results: parent = KEY, "Parent Link" = KEY, issue in linkedIssues("KEY", "initiates"). Filter client-side to issuetype in (Epic) unless nothing is an Epic (then keep all).
4POST /rest/api/3/search/jqlChildren of all epics in one query per 50 epics: parent in (E1, E2, …) OR "Epic Link" in (E1, E2, …). Paginate with nextPageToken, maxResults: 100.

Fields requested on every issue: summary, issuetype, status, assignee, parent, timeoriginalestimate, timeestimate, timespent, duedate, resolutiondate, updated plus the resolved Start date, Sprint and Story Points ids. Aggregate time fields are not trusted; sums are computed from children so an epic's own estimate never double-counts.

The legacy GET /rest/api/3/search with startAt pagination has been deprecated by Atlassian in favour of /rest/api/3/search/jql with token pagination. The pure request builders in packages/jira hide this so a change of endpoint is one file.

Rate limits: Jira returns 429 with Retry-After. The transport layer retries once after the given delay; the refresh flow surfaces a toast otherwise. A refresh of an initiative with ~15 epics and ~400 children is ~6 requests.

7. On-track and buffer math

All of this is pure, in packages/core/src/tracking.ts, unit-tested with fixtures. Inputs: the baseline Project, all Team[], the tracker's JiraSnapshot and epicMap, and today (ISO). No DOM, no Date.now inside.

7.1 The two plans

const buffered   = project.plan ?? runPlan(project, teams, FIXED_TS, opts);
const unbuffered = runPlan({ ...project, buffer: 0 }, teams, FIXED_TS, opts);
// opts = { mode: project.planMode ?? "balanced", lookahead: project.planLookahead ?? 5 }
  • Unbuffered finish U = max end over unbuffered.assignments. Buffered finish B = same over buffered.
  • Schedule buffer bufferDays = working days in (U, B] (weekdays only; team off-days ignored at this aggregate level — the two plans already respect them). If the stored plan is stale (project edited after plan.generatedAt) the panel says so and offers "Run plan".
  • Effort buffer = Σ non-excluded estimateDays × buffer/100. Shown for information; roundingBufferDays is shown alongside as extra slack.

7.2 Planned cumulative curve

plannedDone(d) = Σ a.estimateDays  for a in unbuffered.assignments where a.end ≤ d
plannedTotal   = plannedDone(+∞)

Because the unbuffered plan has buffer = 0, a.estimateDays is the raw estimate; the curve is in plan days, not calendar days, so people's speeds do not distort it.

7.3 Epic completion from Jira

completion(e) =
  e.statusCategory === "done"                 ? 1
: e.totals.spentSec + e.totals.remainingSec > 0 ? spentSec / (spentSec + remainingSec)
: e.totals.all > 0                            ? e.totals.done / e.totals.all
: 0
// clamp to [0, 1]; a done child contributes remaining = 0 regardless of its field value

Time tracking is the primary signal ("tasks that are timed"); the count fallback keeps un-timed epics from reading as 0% forever.

7.4 Earned days, earned schedule, variance

plannedDaysOf(plannerEpicId) = Σ estimateDays of that epic's non-excluded tasks   // raw, unbuffered
earned(today) = Σ over jira epics e with epicMap[e.key] = P (P ≠ null):
                  plannedDaysOf(P) × completion(e)
                // several Jira epics may map to one plan epic; their completions are
                // weighted by their Jira original estimates (or equally when none)

ES  = earliest date d such that plannedDone(d) ≥ earned(today)      // "the plan was here when it had earned this much"
      (projectStart − 1 working day when earned = 0)
variance   = workdays(ES → today), negative when ES is before today  // + ahead, − behind
bufferUsed = clamp(−variance, 0, bufferDays)
overrun    = max(0, −variance − bufferDays)
projectedFinish = U shifted by −variance working days

on-plan|variance| ≤ 0.5"On plan"
using-buffer0 < bufferUsed < bufferDays"Using buffer: 5.0 of 20 days (25%)"

7.5 Worked example

Plan without buffer: 100 plan days, finishes 2026-11-28. Buffer 20% → buffered plan finishes 2026-12-26, i.e. 20 working days of schedule buffer.
Today is 2026-09-13, working day 30. plannedDone(today) = 32.0. Jira says the mapped epics have earned 27.0 plan days.
The unbuffered curve first reaches 27.0 on working day 25 → ES = day 25 → variance = −5.0.
bufferUsed = 5.0 / 20 = 25%, status using-buffer, projected finish 2026-11-28 + 5 working days = 2026-12-05.
Secondary check: Jira remaining 61 days vs plan remaining (100 − 27 = 73 plan days at raw estimates). Shown side by side; a big gap either way is a hint that estimates and Jira have drifted.

7.6 Samples

Each successful refresh appends a TrackerSample (one per calendar day; a same-day refresh replaces). The panel shows the last 10 as a table and a tiny inline bar chart of varianceDays. Samples are part of the tracker row so they sync.

8. Sprint planning section

  • Candidates: children from the snapshot with statusCategory ≠ done, grouped by epic, searchable; a "hide issues already in a Jira sprint" filter (uses the Sprint field).
  • Draft row defaults: estimate = Jira remaining (in days) if > 0, else original estimate, else the mapped plan epic's mean non-excluded task estimate, else 1. Start = sprint start. Assignee = the Jira assignee if a Planner member has the same display name (case-insensitive), else empty.
  • Due date: simulateSpan(fromISO(start), Math.max(1, Math.ceil(estimateDays / speed)), offDays) with speed = member speed × the baseline project's team velocity for that member's team (or 1), and offDays = the member's team off-days (helpers: their own). Same function the scheduler uses, so numbers agree with the plan.
  • Auto-stack per person: in list order, each of a person's items starts the working day after the previous one's due date. Manual edits to start are kept until the next auto-stack.
  • Flags: due > sprint end → "won't finish in sprint" (orange); Σ days per person > working days in window − that person's off-days → "over capacity" (red count badge on the person); no assignee → grey.
  • Mini Gantt: personRows() from planLayout.ts over synthetic Assignments built from the draft, rendered with the existing GanttByPerson + DateGrid, range = sprint window ± 2 days. The baseline plan's assignments whose epic maps to the same Jira epics are passed as faint background bars (new optional prop).
  • Write-back (opt-in): PUT /rest/api/3/issue/{key} with { fields: { [startDateFieldId]: start, duedate: due } }. Preview modal → explicit confirm → per-issue result list → applied recorded on the item. Available only when the transport canWrite and settings allowWrites are both true.
